# Goal
Migrate the ONNX specs from C++ source code to markdown with frontmatter.

## Constraints
- The migration MUST be loss-less.
- The md files will become the new source of truth and must be easy and obvious to maintain
- The specs must remain programmatically accessible. The public API of the onnx package must remain unchanged.
- All the tooling that is used to manage the specs MUST be fully typed and DRY


## Migration plan
During cmake configure cpp files are generated from the md spec files.
These files MUST NOT be create in the regular source tree (probably in the build directory instead).

Operators are currently registered in c++ code under onnx/defs using the `ONNX_OPERATOR_SET_SCHEMA` (and `ONNX_ML_OPERATOR_SET_SCHEMA`) macro.
Operators that do not follow the following pattern are ignored for now.

Here is an example for the `Mod` operator:
```
ONNX_OPERATOR_SET_SCHEMA(
    Mod,
    13,
    OpSchema()
        .SetDoc(Mod_doc)
        .Attr(
            "fmod",
            "Whether the operator should behave like fmod (default=0 meaning it will do integer mods); Set this to 1 to force fmod treatment",
            AttributeProto::INT,
            static_cast<int64_t>(0))
        .Input(0, "A", "Dividend tensor", "T", OpSchema::Single, true, 1, OpSchema::Differentiable)
        .Input(1, "B", "Divisor tensor", "T", OpSchema::Single, true, 1, OpSchema::NonDifferentiable)
        .Output(0, "C", "Remainder tensor", "T", OpSchema::Single, true, 1, OpSchema::Differentiable)
        .TypeConstraint(
            "T",
            OpSchema::all_numeric_types_ir4(),
            "Constrain input and output types to high-precision numeric tensors.")
        .TypeAndShapeInferenceFunction([](InferenceContext& ctx) {
          propagateElemTypeFromInputToOutput(ctx, 0, 0);
          if (hasNInputShapes(ctx, 2))
            bidirectionalBroadcastShapeInference(
                ctx.getInputType(0)->tensor_type().shape(),
                ctx.getInputType(1)->tensor_type().shape(),
                *ctx.getOutputType(0)->mutable_tensor_type()->mutable_shape());
        }));
```

This code must be refactored to read the spec information from cpp files autogenerated from the markdown-spec files.
In particular, the chained method calls are supposed to be reduced.
All invocations of `SetDoc`, `Attr`, `Input`, `Output`, and `TypeConstraint` on `OpSchema()` are to be removed and replaced with a single `.FillUsing(Mod_v13_FillSpec)` where `Mod_v13_FillSpec` is an auto-generated function.
The `Mod_v13_FillSpec` contains all the information that was set by the other methods and completely supersedes them.
The `FillUsing` call should be the first in the `OpSchema()` chain.
All other methods in the chain MUST remain untouched.
All registrations that do not follow the ONNX_OPERATOR_SET_SCHEMA + OpSchema-chain pattern are to be ignored.
Ignore other outer macros.

Some operators use `FillUsing(MathDocGenerator(...)` which is a special case.
Ignore it for now.


### Deterministic tree-sitter script

The refactor is very large and MUST be done ENTIRELY using clean and understandable script.
The script SHOULD use tree-sitter to parse the C++ files to find the above pattern and the span of the methods that can be removed.
The script must keep track of the currently used doc string variable names (e.g. `Mod_doc`) so that they can be auto-removed later.

### Process

Pixi is available and MUST always be used where applicable.

1. Develop the tree-sitter script
2. Wait for user feedback
3. Provide a report on how many ops can/cannot be migrated using the script. Wait for user-clarifications here.
4. For each cpp file under onnx/defs:
   1. Run gen_spec.py for all ops that can be migrated using the script
   2. Migrate theses ops
   3. Run `pixi run lint`
   4. Run `pixi run install`
